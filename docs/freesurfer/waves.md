# FreeSurfer 8.2.0: the waves and the layout

**Closed to FreeSurfer clean-room implementers.** Written from FreeSurfer's source (its call
graph, `code.md`) by a replica-side agent (`docs/porting-guide.md` §1). What a clean-room
implementer needs of it (a crate's name, an item's number) comes through its brief.

Sub-task 6 of FreeSurfer's preparation (relay 6): the waves of [the plan](../freesurfer-plan.md)
checked against the inventory and put in the user's order, the dependency map, and the crates of
`crates-freesurfer/` and of the clean rooms. The order of work is [queue.md](queue.md); one
porting card per program is in `cards/`. The tables between `<!-- waves.py: ... -->` markers are
generated by `validation/investigations/freesurfer-inventory/waves.py` (§7), with its
machine-readable output [waves.toml](waves.toml); the prose is written by hand. Relay 8 brought it
in line with the user's decisions of 2026-11-12 (the placement table's, W1 to W6 below) and gave
the queue's items stable numbers ([queue-ids.toml](queue-ids.toml)).

## 1. The order, and what it changes in the plan

**The user's order** (2026-11-12, decision log "FreeSurfer's borrowed pieces and its two
streams"): the programs both streams share first, then the classic-only ones, with the v8-only
networks as a parallel track. So:

| Wave | What | Change |
|---|---|---|
| 3.1 Foundations | the formats, the image and surface structures, FreeSurfer's maths, random numbers and messages; plus x87 80-bit arithmetic, the borrowed pieces of the placement table (GSL's generators alone in `larmorx-gpl`, Burkardt's spline, the clean-room pieces the replicas use), the VNL routines and C-library behaviours the replicas need, a unit oracle | grown (§3) |
| 3.2 Volumes | the volume programs both streams run, and fMRIPrep's volume and registration programs | corrected |
| 3.3 Atlas | the GCA programs both streams run | corrected |
| 3.4 First surfaces | tessellation to the fixed, remeshed surface | corrected |
| 3.5 Final surfaces and statistics | placement, registration, parcellation, statistics; fMRIPrep's surface programs and `bbregister` | corrected |
| **3.6 The classic-only programs** | `mri_watershed`, the Talairach chain, `talairach_afd`, `mri_ca_label` | **new** |
| **N The v8 networks** | the inference core, the four network programs, their scripts and what only those scripts run | **new: a parallel track** |
| **3.7 `recon-all`** | the script and its helpers | **was 3.6** |

**fMRIPrep's programs outside `recon-all`** (`mri_coreg`, `mri_robust_register`,
`mri_robust_template`, `bbregister` with `mri_segreg` and `tkregister2_cmdl`, `mri_vol2surf`,
`mris_convert`, `mris_expand`, `mri_surf2surf`, `mri_vol2vol`) belong to no stream: they come with
the shared programs, in the waves their code belongs to (3.2 and 3.5), as the plan has them for
their early value. **The N track** runs beside 3.2 to 3.5: its first item (the inference core) and
the four network programs need only 3.1's formats; its scripts (`fs-synthmorph-reg`,
`rca-talairach`, `mri_mcadura_seg`, `mri_vsinus_seg`, `mri_entowm_seg`) wait for 3.3, because
`fs-synthmorph-reg` runs `mri_ca_register -invert-and-save`.

**The plan's wave table, corrected** (from programs.md's measured stages, relays 1 and 2; the
reasons per program are in §2's notes):

- **3.2:** adds `AntsN4BiasFieldCorrectionFs` (8.2.0's default intensity correction, through

  `talairach_afd` (classic only: 3.6), `mri_concatenate_lta` (only `fs-synthmorph-reg` runs it:
  N). `mri_nu_correct.mni`'s N3 (`nu_correct`) goes to *later* (only with `-no-ants-n4`).
- **3.3:** `mri_em_register` and `mri_ca_normalize` run in **both** streams (the plan: classic
  only); `mri_ca_register` runs fully in classic and through `-invert-and-save` in v8.
  `mri_ca_label` is classic only (3.6); `mri_relabel_hypointensities` reads the white surfaces
  (autorecon3: 3.5); `mri_segment_hypointensities` is not run by 8.2.0 (out of the waves). The
  networks go to N.
- **3.4:** adds `mris_topo_fixer` (when `mris_fix_topology` leaves a defect), `mris_remesh` (on
  by default), `mris_defects_pointset` and `mri_label2label` (from 3.5: `defect2seg`, stage 52,
  runs both first).
- **3.5:** adds `mris_curvature_stats`, `mris_label2annot`, the scripts `label-cortex` (with its v8
  helpers `mri_cor2label`, `fscalc`, `mri_mergelabels`), `vertexvol`, `rca-surfreg` and
  `fsr-getxopts`, `bbregister`'s `mri_segreg` and `tkregister2_cmdl` (CorTechs' terms: its replica
  in `larmorx-nc` as its own program, its clean room here; the user, 2026-11-12),
  `mri_relabel_hypointensities`, and the surface halves of `mri_segstats` and `mris_calc`.
- **N:** the four network programs (`mri_sclimbic_seg` added, three models), their scripts,
  `csvprint` (SynthSeg's volumes), and `mri_concatenate_lta`, `mri_warp_convert`, `mri_diff`,
  `mri_compute_seg_overlap` (only the v8 scripts run them).
- **3.6:** the classic stream's Talairach registration, `talairach_avi` with `mpr2mni305` and the four
  4dfp programs, is a clean room only (the user, 2026-11-12: Washington University's Talairach
  tools; `talairach_avi` itself carries MGH's notice, but the decision names it); `avi2talxfm`,
  `mri_matrix_multiply`, `fs_temp_dir` and the QA check are FreeSurfer's and get both.
- **later:** `nu_correct` (MNI's N3), MINC's `talairach` (the fallback after two failed Talairach
  checks), MARS (P-13: later, the user).

## 3. The dependency map

**How it is computed.** Every file the 72 compiled default-path programs reach (code.md's core
view) belongs to one module (the table below); a few functions belong to another module than
their file's (`FUNCTION_MODULES`: GSL's generators and Burkardt's spline inside `numerics.cpp`,
which the placement table puts elsewhere than FreeSurfer's code); every module has the wave that
brings it. Each reached function goes to one queue item: the program's own item when one program
alone reaches it and that program's wave is not earlier than the module's (except the modules
that are always an item of their own, `OWN_ITEM`: `gpl.gsl`, `fs.spline`); otherwise the module's
item. The parser modules W3 names (`perm.gifti`, `perm.dicom`, `perm.json`) have items by role
(the parser, the reader, the exact writer: `W3` in `waves.py`), not by lines. A program
of an earlier wave that reaches a later module's functions has option paths that **wait** for that
module; they are completed in that wave ("the option paths ..." items of the queue). So every
line of FreeSurfer's source is counted once, in the item that brings it.

**A static superset.** The call graph follows every call a program's code can make, not what a
run executes: `mri_add_xform_to_header` "reaches" 6,014 lines of the GCA code because `MRIread`
can read a `.m3z` morph as a volume; on recon-all's call it runs none of them. The sizes below are
upper bounds for full completeness (every option of every program, which the user's rule asks
for), not the default paths' cost. The unit oracle (queue item 3.1-02) could measure the default
paths exactly (a coverage build replaying each recorded step): later, an extra on the lab's
server (§6, W6, decided).

**Outside the graph.** The call graph covers FreeSurfer's tree: the statically linked ITK 4.13.2
and VNL code (N4's filters, the denoiser's, `vnl_svd`, `vnl_random`, ...) and the Python of the
network programs are not in its lines. They come through the permissive items (3.1's VNL and
random-number items, the N4 and denoiser checks in `AntsN4BiasFieldCorrectionFs`'s and
`AntsDenoiseImageFs`'s items, N's inference core); the scripts' and Python programs' own lines
are given in their rows.

**Why 3.1 grew.** FreeSurfer's library is one block (`libutils`): every compiled program links
it, and its volume reader alone reaches the DICOM probe, GIFTI through expat, MINC's `.xfm` reader
and the surface structure. With the rule above, 3.1 takes the volume side of the library (the
formats, the `MRI` structure, transforms, labels, colour tables, the filters) and the surface
structure with its I/O (reading a surface computes its metric properties); the GCA code waits for
3.3 and the rest of the surface library for 3.4.

## 4. The crates

Four kinds of code, kept apart by licence (CLAUDE.md rule 1; the placement table,
third-party.md §9, as the user decided it on 2026-11-12).

**The replicas: the workspace `crates-freesurfer/`** (FreeSurfer's licence, the wheel and program
`larmorx-freesurfer`; CLAUDE.md rule 3). It builds the Apache crates by path, never `crates-gpl/`
or `crates-nc/`. Library crates in layers, each depending only on the ones above it:

| Crate | Modules | Depends on |
|---|---|---|
| `larmorx-freesurfer-core` | `fs.core` (messages, diagnostics, environment, version stamps, ROMP), `fs.maths` (matrices, numerics wrappers, `fs_powell`, `fs_lbfgs`, statistics), `fs.spline` (Burkardt's 2006 spline, crediting him: P-09, published normally) | `larmorx-core` |
| `larmorx-freesurfer-mri` | `fs.mri` (the `MRI` structure and `VOL_GEOM`: allocation, free, header copies, the voxel-to-RAS matrices, voxel access, the colour table's structure an `MRI` carries; queue 3.1-55) | core |
| `larmorx-freesurfer-io` | `fs.io` (MRIread/MRIwrite, tags, the format probe), `fs.labels` (colour tables, annotations, labels, `register.dat`, point sets), `fs.dicomread` (DICOM input, queue 3.7-14 and 3.7-15) | core, mri, `larmorx-io` |
| `larmorx-freesurfer-volume` | `fs.volume` (voxels and frames on the structure, transforms, resampling, warp fields, CMA), `fs.bspline` (EPFL's B-splines) | core, mri, io |
| `larmorx-freesurfer-filter` | `fs.filter` (filters, normalisation, segmentation helpers, flood fill) | volume |
| `larmorx-freesurfer-surf` | `fs.surfio` (the surface structure and its I/O), `fs.surf` (the rest of the surface library), `fs.mars` (later) | volume |
| `larmorx-freesurfer-deform` | `fs.deform` (surface deformation) | surf |
| `larmorx-freesurfer-defect` | `fs.defect` (the topology fixer's defects) | deform |
| `larmorx-freesurfer-gca` | `fs.gca` (GCA, GCA morphs, MRI morphs) | filter, surf |
| `larmorx-freesurfer-robust` | `fs.robust` (Reuter's robust registration) | volume |

and the programs, one crate per wave, one module per program inside it:
`larmorx-freesurfer-volumes` (3.2), `-atlas` (3.3, and 3.6's `mri_ca_label`), `-topology` (3.4),
`-cortex` (3.5), `-classic` (3.6), `-networks` (N), `-recon` (3.7: `recon-all` and its helpers,
which run the other crates' programs in-process), and `larmorx-freesurfer-cli` (the program
`larmorx-freesurfer`, the wheel, the registry, the settings overlay of larmorx's three options).

**Calls against the layers** (the orchestrator's decision on 3.1-25, 2026-11-13). FreeSurfer's C
and C++ files call each other in every direction, and a Rust crate depends only on the crates below
it. The **data structure is low and the functions that read files are above it**: the `MRI` structure
(`fs.mri`, its own crate under `fs.io`) holds what every reader builds, so `fs.io` no longer needs
`fs.volume` for it; a structure's methods that read or write files (`VOL_GEOM::read` and `::write`,
`MRI::write`) go up to `fs.io`, as Rust functions on the structure. What remains against the layers
is measured by `layering.py` (the call graph's edges, `callgraph.py --edges`): after the move, the
reached functions of `fs.io` still call 26 functions of `fs.volume` directly (970 lines; 34 with `fs.labels` and `fs.dicomread`, the rest of the crate) (`MRIcopyFrame(s)`,
`MRIclear`, `MRISeqchangeType`, `mri_reshape`, `MRIresample` for GCA files, `MRIreverseSliceOrder`,
the warp-field files, CMA's outlines, ...), and the other modules a few each (`layering.py` without
options lists every pair). Each such call is settled when its item ports the caller, in this order of
preference: the callee moves down with the structure when it only touches the structure; the caller
moves up to the module of its callee (a reader that resamples belongs with the resampler); or the
lower crate takes the operation as an argument (a function or trait the higher crate supplies, as C
does with its function pointers). Some edges are the static index's over-approximations (a local
variable named like a function, `sx` in `MRIsetVox2RASFromMatrix`); a port checks each against the
source before acting on it.

**The replicas in the other companions** (the user, 2026-11-12, "No waiting for permissions"):

| `larmorx-gpl-gsl` (`crates-gpl/`) | `larmorx-gpl`, alone | GSL 1.8's RANLUX389 and distributions as `numerics.cpp` transcribes them (P-08, the module `gpl.gsl`, queue 3.1-53): the clean room's bit-exact reference; no FreeSurfer program links it (`mri_coreg`'s and `mris_expand`'s replicas use the clean room, 3.1-05) |

**The permissive replicas: the main package.** Third-party pieces under permissive terms (P-01 to

`lx.freesurfer` (the dispatch between the replica program and the clean room), best written by an
agent that never read FreeSurfer's material, because these files hold the clean rooms' side too.

**Names.** `larmorx-freesurfer-*` are replicas (FreeSurfer's licence), `larmorx-fs-*` clean rooms
(Apache-2.0), `larmorx-nn` the networks' inference core (§6, W2: accepted).

**Parallel agents never touch the same files.** One item is one module's files or one program's:
`src/<module>/` or `src/<program>/` in its crate. The pieces of one module come one after the
other (one agent per module at a time); programs of one crate can go side by side. The shared
touch points are one `pub mod` line in a crate's `lib.rs`, its `Cargo.toml`, the registry of
`larmorx-freesurfer-cli` and the golden registry: minimal changes, merged by the orchestrator.
A replica's program and its clean room are always different crates (and different agents).
