# The orchestrator's procedures

Moved verbatim from CLAUDE.md's "Working on this machine" on 2026-11-02, when CLAUDE.md was
made leaner (the user, 2026-11-02): the orchestrator merges, publishes and launches; agents do
not. The steps as scripts: `scripts/orchestration/` (its README). Each part's brief, report and
handoff: `docs/parts/`.

- **Merging an agent's work: the checklist** (the user: "Make sure everything works before merging"). Nothing reaches `main` or GitHub before steps 1-5 and 5a pass on the merged tree in the main checkout:
  The steps as scripts: `scripts/orchestration/` (README: one command per step). Each part's brief, report and handoff go into `docs/parts/` at its merge.
  0. Start from a clean tree; chain the merge with `&&` and check `.git/MERGE_HEAD`. On 2026-10-11 an uncommitted file made `git merge` abort, and the checks then ran on the old tree.
  1. The three Rust workspaces: `cargo fmt --check`, `clippy -D warnings`, `cargo test --locked`, in the root, `crates-gpl` and `crates-nc`.
  2. `maturin develop --release`, then `pytest tests/python tests/golden validation/tests`.
  3. `ruff check`, `ruff format --check`, `scripts/check_spdx.py`.
  4. The parity smoke tier against the real oracles (`verify-merge.sh` runs it in parallel, `scripts/orchestration/parity_smoke.py`; `--serial-parity` serially).
  5. Re-run the new or changed tool's standard-tier parity yourself, from the committed merge (a clean tree, so the record's commit is clean), and compare with the agent's record. The re-run serves the agent's runs of the originals from the oracle-output cache (the record's header says how many); `--oracle-cache refresh` re-runs and compares them.
  5a. **The clean-room audit** (the user, 2026-11-06: "the only thing most important to prove is that the agents did not look directly the source code"; [validation/clean-room-audit.md](validation/clean-room-audit.md)), on the committed merge, before the push: `scripts/orchestration/cleanroom-audit-merge.sh <checkout> <part> --scratch <the part's scratch folder> [--worktree <its worktree>] [--notes <its NOTES.md>] --summary` (about half a minute). It copies every transcript Claude Code holds that the archive lacks (the part's agents and the orchestrator's session; Claude Code deletes them after 30 days) into `<workspace>/archive/<date>-session-transcripts-<part>/` with their SHA-256 (an agent of the part without a transcript: exit 2), scans every transcript, makes the verdicts from the merged history and runs the gate. **Exit 1 stops the merge**: each `STOP` line is an edit of clean-room code by an agent after it had seen restricted material of that tool's family (an implementer's finding, or another role's edit: the orchestrator's own included), or a commit of clean-room code nobody's record made. Read the call in the dossier (`<workspace>/archive/clean-room-audit/<date>-<part>/verdicts/verdicts.md`, the call verbatim in `verbatim.md`); then either revert the edit (a fresh clean-room agent redoes it) or, when it carries nothing of the upstream (a title, behaviour the spec states, another family's lines, larmorx's own code), judge it in `validation/cleanroom-audit/judgements.toml` and re-run. `JUDGE` lines (slips of other families, headings, files a brief forbade) do not stop the merge: judge them the same way before the next one. With `--summary` the step regenerates `docs/validation/clean-room-audit.json` and `.md` (commit them with the merge; `lxv.sh . cleanroom-audit summary --check` verifies the page); add `--similarity` (about 15 minutes, boxed) when the part changed clean-room code, so the page's similarity figures cover it. **The audit reads each agent's role from its launch description first** (`cleanroom_audit/verdicts.py`, `ROLE_BY_WORDS`): name a replica-side relay with "replica" in its description ("... replica-side relay ..."), a spec writer with "spec writer", and keep a clean relay's description free of the spec writer's words ("spec answers", "behaviour spec", "(spec)": `t2smap`'s clean relay C4, "spec answers in original", came out as a spec writer until `ROLE_BY_DESCRIPTION` named it, 2026-11-12); a description that names no role falls back to the brief, where a part brief that mentions clean-room implementers for its rules makes every relay an implementer (the easy command line, 2026-11-11: its two replica-side relays' allowed reading of `crates-nc/` came out as 87 slips until `ROLE_BY_DESCRIPTION` named them).
  5b. **The evidence backup** (the user, 2026-11-11: "you can make a constant backup in the HDD drive ... But, the main source will be the existing one"): after the audit has archived the part's transcripts, run the workspace's `tools/backup/backup_evidence.sh` (outside this repository; its README there): it copies the transcripts, the archived transcript sets, the audit's dossiers and the cost ledger to the backup disk, never deleting there, every copy verified by SHA-256; an hourly user timer runs it too.
  6. **Integrate and harmonize the documents** (user, 2026-10-23: "I just want the implementations and docs correct after the agents finished their job"): put each agent's `HANDOFF.md` into the shared documents; re-read every shared document the merge touched so it tells one consistent story (the defect register's table, history paragraph and counts, `docs/api/upstream-defects.md`, README, the validation index, next-steps, [docs/status.md](status.md) and CLAUDE.md's short "Where things are", the site's status, navigation and Validation page) and **update the site's Roadmap page** (`content/roadmap.md`, user, 2026-10-29: "It should update whenever you complete a step or task": the completed step moves to "Completed" with its date, the next step's status changes, "Last updated" changes); recount the register's **decide** entries and list every one under "Waiting for the user". After merging two parallel branches, re-record the golden checksums from the merge (`scripts/record_golden.py`; the values must not change) and re-export the site's summary.
  7. Commit, check for AI attribution, push, then watch CI on all six platforms.
  8. Once CI is green, delete that agent worktree's Rust build caches (`target/`, `crates-gpl/target/`; regenerable), keeping only the newest worktree's cache as a seed for the next agent (user, 2026-10-19: 30 merged worktrees had grown to 190 GB). Never delete a worktree's source or branch.
- **Reading CI results without a login:** GitHub serves job logs only to logged-in users. Golden mismatches, failing `cargo test` tests and build errors (`scripts/ci_cargo_failures.py`, since 2026-10-12), and every other failing Python test or collection error (`tests/python/conftest.py`'s `pytest_terminal_summary`, since 2026-11-10: a golden case that raises included) are printed as workflow annotations, which `https://api.github.com/repos/karellopez/larmorx/check-runs/<job id>/annotations` serves without a login. Each job's step results: `https://api.github.com/repos/karellopez/larmorx/actions/jobs/<job id>`. GitHub's Windows runners give the temporary directory as an 8.3 short path (`C:\Users\RUNNER~1\...`): tests must not assume a temporary path free of `~` or blanks.
- **Launch worktree agents from inside this repository** (`cd <workspace>/larmorx` right before the Agent call): the harness creates the worktree in the repository of the current directory. On 2026-10-20 A5 part 2 was launched from `larmorx_documentation` and its worktree landed there.
- **Making a release** (since the first, 0.1.0rc1, 2026-11-11; every step for any maintainer, with what to do when a job fails: [RELEASING.md](../RELEASING.md)): the orchestrator pushes and tags, the user approves the uploads; nothing needs a login or a token.
  1. **The release commit** (the version by `scripts/release/set_version.py <v> --date <day>`, `CHANGELOG.md`'s section with its statuses table by `changelog.py <v> --write-statuses`, the README's status line) merged by the checklist above, and CI green on all six platforms. A later merge that changes `validation/tools.toml` before the tag needs `changelog.py <v> --write-statuses` again (the tag's `check` job stops otherwise). After the merge, step 2's `maturin develop --release` brings the shared venv's metadata to the new version (`tests/python/test_smoke.py`'s 7 version tests fail in agents' worktrees until then).
  2. **The dry run, of the exact commit to be tagged:** `git push origin +<sha>:refs/heads/release/dry-run`, then `python3 scripts/orchestration/watch_ci.py <sha> release/dry-run` (each job's result, a failed job's annotations); about 40 to 55 minutes, about 400 job-minutes. It passes when every job but the release-only ones is green (check, sdist, wheel x6, programs x6, test x6, sdist-install, container x2, assemble); the normal notices: the version is not on PyPI yet and, for a commit not on main yet, `CI-GREEN NO`. The files and their sizes: assemble's notice at `https://api.github.com/repos/karellopez/larmorx/check-runs/<assemble's job id>/annotations`.
  3. **Before the tag:** the three environments by the public API (`https://api.github.com/repos/karellopez/larmorx/environments` and each one's `deployment-branch-policies`: `pypi`, `pypi-gpl`, `pypi-nc`, each with the reviewer karellopez, administrators' bypass off, one tag rule `v*`); the date (`CITATION.cff`'s `date-released` and the CHANGELOG heading name the day of the tag; on another day `set_version.py <v> --date <day>` and the heading in one commit, which runs CI, and a dry run of it).
  4. **The tag:** `git tag -a v<v> -m "larmorx <v>" <main's sha>`, `git push origin v<v>`, `watch_ci.py <sha> v<v>`. When `assemble` has passed, the run waits for the three deployments: tell the user then, with the run's link (they tick all three in "Review deployments" and approve). Then, by themselves: the three uploads (larmorx's waits for its companions), `container-push` (the two images to `ghcr.io/karellopez/larmorx`), the GitHub Release and `verify-pypi` on the six platforms. A job that fails after the approval: "Re-run failed jobs" (the user, in the browser; never "Re-run all jobs"; a partial upload finishes so: `skip-existing`), `RELEASING.md` step 5.
  5. **After the upload:** the user makes the image package public once (D17: github.com/users/karellopez/packages/container/larmorx -> Package settings -> Change visibility -> Public); then here `apptainer pull docker://ghcr.io/karellopez/larmorx:<v>`, `check_install.py` from PyPI in a clean Linux image through Apptainer (`RELEASING.md` step 6) and `validation/investigations/release-0.1/win_check.sh <v>` on the Windows helper (it checks that nothing is left there); then the site's release pages, merged and pushed only now (their install lines, download addresses and image names exist only after the upload): the part's site handoff by `apply_handoff.py --site`, `tools/build.py` with 0 problems, and the Roadmap page.
  6. **A final release** (0.1.0 after rc1) repeats steps 1 to 5 (`RELEASING.md` step 7).

## The agents rule as CLAUDE.md stated it until 2026-11-02 (verbatim)

CLAUDE.md now states the current rule; its history, kept here and in the decision log:

- **One agent at a time, in bounded parts with a stop after each** (user, 2026-10-10 and 2026-10-17): the user watches the weekly usage limit (only they can see it, with `/usage`), and starts each next part. A second agent in parallel **only when the user explicitly asks** for it (user, 2026-10-22: "Lets keep the one agent at the time in the docs. But you can use 2 agents only when I tell"; that day A5 part 3 and A6 ran together); never more than two unless the user says so (2026-10-24: four at once, for the evidence infrastructure and FSL, "I will tell you if something gets wrong"). **From 2026-10-26: one agent at a time** (user: "I would like to continue the development but with 1 agent at a time"). **From 2026-11-02: two at once, by role, with relay agents** (user: "can we try this new method after this flirt clean room? The idea is to go faster, spending less tokens and also maintaining quality"; decision log 2026-11-02): a replica (and its spec) beside the previous tool's clean-room original, which never touch the same files; never more than two. On the main machine (32 threads) one agent may use up to 28 threads (cargo `-j 28`, parity `--jobs` to match); parallel agents split them: two at most 14 each, four at most 7 each; the orchestrator merges them one after the other.
- **Agents at once: two at most, by role, since 2026-11-02** (above; before: one at a time from 2026-10-26; a two-agent trial on 2026-10-11 was stopped the same evening to stay within usage limits; four parallel agents once exhausted the session limit and were killed mid-task). Two agents: 14 threads and at most 32 GiB of memory boxes each; the orchestrator's verification beside them at most 32 GiB and 8 threads. Brief every agent to commit as soon as its work passes the gates; when pausing one, ask for a WIP checkpoint commit and a NOTES file first.
