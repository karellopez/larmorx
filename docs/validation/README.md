# Validation records

One record per validated tool: larmorx compared, case by case, with the reference implementation it replicates, on the catalog of `larmorx-testdata` (github.com/karellopez/larmorx-testdata, next to this one; its data panel, `docs/panel.md` there, is the fixed set every tool is validated on). Each record states the thresholds, the environment, every expected divergence with its reason, and the result of every case. They are generated by the [validation package](../../validation/README.md). The same suites run under pytest (`tests/parity`); CI skips them until the test data are published.

The table is generated from [validation/tools.toml](../../validation/tools.toml) and each
record's JSON (`python -m larmorx_validation tables`; `--check` fails when it is stale).

**Random testing.** A night at a time, every tool also runs random valid inputs and option
combinations against its original ([difftest](difftest.md)): the same runners decide each case,
a difference is shrunk and triaged (`validation/difftest/triage.toml`), and a fixed one stays as a
permanent case of the tool's suite (`difftest/<id>`, in the smoke tier). The first night
(2026-10-25, 6.2 h, seed `20261025`): 34 880 cases; 31790 agree, 3 explained, 1350 notice, 394 undefined, 1227 differ, 76 memory, 38 timeout; 58 groups of differences: 34 fixed in larmorx, 6 defects of the originals in the register, 17 open for the clean-room originals' agents, 1 the harness's own; 76 heavy cases queued (40 since run here: 26 agree, 14 notices that changed no value; 11 beyond any machine, met by larmorx's guards; 25 waiting for a larger machine).

**Memory.** For the same call larmorx needs at most the original program's peak memory, plus the
Python interpreter's few MiB (the user, 2026-10-25): `tests/parity/test_memory_peak.py` holds 13
mid-size calls of the ANTs image programs at ANTs' peak plus 8 MiB, bit for bit in `reproduce`
(`docs/findings/ants-image-programs.md`, `ants-n4.md`, `ants-denoise.md`, "Memory against
ANTs"), and five calls of BET's programs (bet2 with its outputs, `bet -R`, `bet -F` on a series,
betsurf; 2026-10-26) at FSL's peak, FSL's bytes in `reproduce`; the other tools are still to
measure ([next-steps](../next-steps.md)).

**Against a real fMRIPrep run.** [fmriprep-stages](fmriprep-stages.md) runs larmorx's tools,
step by step, on the inputs and parameters fMRIPrep 25.2.6 itself used (read from nipype's
working directory of an oracle run), and compares them with fMRIPrep's own output at each
step; where they differ, the step is re-run in fMRIPrep's image and with the oracle builds to
separate thread effects, ANTs' version, glibc's maths and larmorx. It is a record of the
pipeline's stages, not of one tool, so it has no status of its own; it also lists the tools
larmorx does not have yet. One record per oracle run:

|---|---|---|
| [fmriprep-stages](fmriprep-stages.md) | ds000005 sub-01 | three BOLD runs, no field maps, no slice timing |
| [fmriprep-stages-ds005040](fmriprep-stages-ds005040.md) | ds005040 sub-002 | PEPOLAR field map (`topup`) applied with the Jacobian, slice timing: both 3dTshift implementations, PIPE-03 on a real field map |
| [fmriprep-stages-ds005454](fmriprep-stages-ds005454.md) | ds005454 sub-16 | two T1w (the pre-template N4), `phasediff` field map, an oblique multiband BOLD of 280 volumes |
| [fmriprep-stages-ds005752](fmriprep-stages-ds005752.md) | ds005752 sub-ON01016 | two BOLD runs with slice timing; its direct `fieldmap` is not used by fMRIPrep (no `IntendedFor`) |

[fmriprep-stages-float](fmriprep-stages-float.md) re-ran the antsApplyTransforms stages of
ds000005 (A06, A11, F08, F09, F12) after larmorx learnt `--float 1` (2026-10-11); the
regenerated [fmriprep-stages](fmriprep-stages.md) now covers them, so it is kept as history.

These records compare larmorx with the original tools on Linux x86-64. That the other five
platforms reproduce larmorx's own Linux x86-64 output is checked by the golden tests, in CI:
[golden.md](golden.md).

**The original programs run once.** Every parity suite runs the originals through the
[oracle-output cache](oracle-cache.md): a run seen before (the same oracle build, inputs,
arguments and settings) is served from `<workspace>/oracles/cache`, so re-making a record runs
only larmorx; each record's header says how many original runs came from the cache. Runs whose
result the original itself varies (its clock, races, the thread bands of programs that vary,
memory it never wrote) always run. A record made from the cache is byte-identical, apart from
that line and the timings, to one made without it. Measured on a busy machine (other agents ran
beside it; load average 8 to 31): the smoke tier's records took 2021 s without the cache and
694 s warm, `pytest tests/parity` 94 minutes and 27, `ants-registration`'s standard record 2.0
hours and 49 minutes (509 of its 657 original runs from the cache); details and the proof in
[oracle-cache.md](oracle-cache.md). Since 2026-10-28 the key keeps the text a program reads in a
path, files named by a pattern and paths with blanks; the cache applies ANTs' clock and memory
rules to every run; and the originals run under a 64 GiB address-space limit
([oracle-cache.md](oracle-cache.md)).

**The ANTs oracle** is ITK 5.4.5 and ANTs 2.6.5 built from the pinned tags by
`scripts/build_ants_oracle.sh` into `<workspace>/oracles/ants-2.6.5`. The records compare
with what the C++ source defines (CLAUDE.md rule 8), so the build must not miscompile it:
GCC 11.4 and 12.3, Ubuntu 22.04's compilers, drop float roundings at `-O3` (GCC bug 110182,
[ants-n4 findings](../findings/ants-n4.md)), and the script stops when its compiler probe
finds that. The oracle in use is built by conda-forge's GCC 14.3.0, installed in a user-level
environment, with ITK's and ANTs' own flags; `BUILD_INFO.txt` records the compiler, the flags
each build used and the probe's result, and the records quote it. The first oracle, built by
GCC 11.4, is kept as `oracles/ants-2.6.5-gcc11-O3`; `LARMORX_ANTS_BIN=<dir>/bin` points any
ANTs suite at another build.

```bash
conda create -p <workspace>/oracles/toolchains/gcc-14.3 -c conda-forge --override-channels gxx_linux-64=14.3.0 gcc_linux-64=14.3.0
T=<workspace>/oracles/toolchains/gcc-14.3/bin
scripts/build_ants_oracle.sh --jobs 4 --cc $T/x86_64-conda-linux-gnu-gcc --cxx $T/x86_64-conda-linux-gnu-g++ --ldflags "-static-libstdc++ -static-libgcc"
```

The commands use the oracle cache (`--oracle-cache use`, the default); `--oracle-cache off` runs
every original program, `--oracle-cache refresh` runs them and compares them with the cache.
