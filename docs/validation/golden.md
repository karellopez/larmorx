# Golden tests: the same output on every platform

Golden tests check that every CI platform (Linux x86-64 and aarch64, macOS Intel and Apple
silicon, Windows x64 and arm64) reproduces larmorx's own **Linux x86-64** output, bit for bit,
for every function (CLAUDE.md rule 10, PLAN.md §11.4, decision D12). They complement parity:

- **Parity** compares larmorx with the original tools, on real data, on the Linux x86-64
  development machine only (most originals do not exist on macOS or Windows).
- **Golden tests** compare larmorx with itself: small inputs generated by the test, checksums
  recorded on Linux x86-64 from a tree whose parity passes, reproduced everywhere in CI.

Replicas and clean-room originals are covered alike. Written 2026-10-11.

## How inputs are made

- **Seeded integers and plain arithmetic.** SplitMix64 (written out in both test files, so the
  Python and Rust inputs agree and nothing depends on numpy's random streams, which numpy does
  not promise to keep), then `+ - * /` and squares, in Python floats or elementwise numpy
  operations. No `sin`, `exp`, `log`, general powers, reductions or matrix products: their
  last bits can differ between platforms. Values are exact integers or correctly rounded
  quotients, so the inputs are the same bits everywhere.
- **Head-like volumes**: noise, a head, a brighter brain with a gradient, a dark ventricle;
  masks with a jagged edge, an enclosed hole and a separate blob; labels by quadrant. The
  grids are oblique (a rotation with rational cosines, from the 3-4-5 and 5-12-13 triangles),
  anisotropic and centred near the origin, so that the transforms and the reference grids
  overlap the images.
- **Sizes:** 24 × 20 × 16 (3D), 16 × 14 × 12 × 4 (4D), 32 × 24 (2D), all under the 32³ voxel
  and 4-volume bounds. **One exception:** 3dTshift refuses fewer than 5 time points, so its
  series is 8 × 6 × 5 voxels by 10 time points (2,400 values in all).

## HDF5 fixtures

The one exception to generated inputs (CLAUDE.md rule 10, user decision 2026-10-16): larmorx's
HDF5 reader (crate `larmorx-hdf5`, A4 part 1) reads storage that only the HDF5 C library
writes, and larmorx's own writer replays ITK's calls only, so golden cases cannot generate
those files on every platform. Five tiny synthetic files are committed instead, in
[`tests/golden/hdf5/`](../../tests/golden/hdf5/), gzip-compressed (14 KB in all; 140 KB
decompressed, most of it the empty space HDF5 allocates for a paged extensible array, a huge
object and global heap collections):

| File | Format | What it holds |
|---|---|---|
| `sb0.h5.gz` | superblock 0, version-1 object headers | symbol-table groups (a group of 12 entries over two B-tree leaves, soft links in the local heap), a dataset whose 40 attributes spill into a continuation, a big-endian double, half, x87 extended and IEEE quadruple floats (both byte orders), fixed-length strings with each padding, variable-length strings, a chunked dataset with shuffle, Fletcher-32 and deflate under a version-1 B-tree with a chunk never written, a compact dataset, a scalar, a committed datatype, a soft link to a group |
| `sb1.h5.gz` | superblock 1 | a chunk B-tree K of 64 (`H5Pset_istore_k`) |
| `sb3-datasets.h5.gz` | superblock 3, version-2 object headers (file format 1.10) | every chunk index: a single chunk (filtered or not), implicit, fixed array (unpaged; paged and filtered), extensible array (index block, data blocks, a super block with filters, a page of a paged data block, the unlimited dimension second), version-2 B-trees (an internal node; filtered); the n-bit filter (a 20-bit float, little- and big-endian integers), the scale-offset filter (float D-scale, big-endian double, integers with a fill value), UTF-8 strings, a chunk never written, a committed datatype, soft links to a group and a dataset |
| `sb3-groups.h5.gz` | superblock 3 | dense groups: 60 links and a 4,200-character name (a huge object) in a fractal heap with an indirect root block; the same with deflate on the heap; a heap filtered by deflate and Fletcher-32; links indexed by creation order |
| `sohm.h5.gz` | superblock 3, a superblock extension | a transform file of 8 affines whose filter pipelines are shared in a list index and whose datatypes, dataspaces and fill values in a B-tree index of the shared-message heap |

- **Made by** [`scripts/make_hdf5_fixtures.py`](../../scripts/make_hdf5_fixtures.py), with
  h5py's low-level API (h5py 3.16.0 on HDF5 2.0.0, the workspace venv): seeded integers and
  their quarters (SplitMix64, as the registry draws its inputs), no image data. Object times
  are off (`track_times`); HDF5 still records them in objects it creates with a default
  property list (the superblock extension, committed datatypes), so the script sets every
  version-2 object header's times to 0 and recomputes its checksum (Jenkins' lookup3; a
  header is changed only if its checksum checks). The script builds every file twice, more
  than a second apart, and refuses if the bytes differ; gzip with `mtime=0` and no name.
  `python scripts/make_hdf5_fixtures.py --check` rebuilds them and compares the
  decompressed bytes with the committed files (another h5py or HDF5 version may write other
  bytes; then re-run the parity cases below before committing new files).
- **Checked against h5py** by the parity suite `itk-hdf5` (cases `hdf5/fixture/*`, smoke
  tier): every dataset as h5py reads it, bit for bit (floats through HDF5's conversion to
  double, so that quadruple precision is compared too), every group's links by name, and
  the shared-message file's transforms as ITK reads them (`antsApplyTransforms`, double and
  float).
- **On every platform** the golden case `hdf5.fixtures` decompresses them into its directory
  and fingerprints what larmorx reads back. Nothing hashes the fixtures' own bytes: they are
  inputs, fixed by the repository.

## What is compared

- For every output: the **SHA-256 of its data** (the values little-endian, in index order),
  with its type and shape.
- For files a tool writes: the **NIfTI header** (the bytes before `vox_offset`, extensions
  included) and the **data** are hashed separately (`.gz` decompressed first); text and other
  files as bytes. `io.nifti1_gz_scaled` also hashes two gzip files as written, so the
  compressor must give the same bytes everywhere too.
- **HDF5 transform files** (`py.transforms.write_h5`): the whole file's bytes, and a
  fingerprint of what larmorx reads back (every group and dataset: names, datatypes, shapes,
  strings; the floating-point values). The bytes include deflate-compressed chunks (zlib-rs
  0.6.8, which picks CPU-specific code paths at run time): on the Linux x86-64 machine it gave
  the same bytes with and without its AVX2 paths at every level (decision log, 2026-10-16);
  the aarch64 NEON paths are checked by CI. A platform whose bytes differ is reported, not
  given a tolerance. The Rust tests `crates/larmorx-io/tests/itk_hdf5.rs` also check, on every
  platform, that larmorx writes four files the ANTs oracle wrote, byte for byte.
- **Bit-identity, no tolerance.** A tolerance needs a documented reason in `docs/findings/`
  (rule 10); there is none today.
- To tell how large a mismatch is, `golden.json` also keeps, per array output, **8 values at
  fixed positions** and the **exact sum** (`math.fsum`). They are about half of its 65 KiB.

## Reading a failure

The test names the case, each output that differs, both hashes and what the samples say:

```text
py.transforms.resample_series differs from larmorx on Linux x86_64 (recorded from 3a1c… on 2026-10-11):
  out.float64: sha256 bca380ad8bb98ce3… expected, 4f73eb1dde5ba30a… found; 2 of 8 sampled values differ, max |difference| 5.7554e-13, max 81 ulp
Outputs saved in …/golden-mismatches/py.transforms.resample_series; `python scripts/record_golden.py --compare <dir>` on Linux x86_64 measures the full difference.
```

The failing CI job uploads the outputs that differ (`.npy` arrays, `.bin` bytes and the files
the tool wrote; at most 50 MB) as the artifact `golden-mismatches-<platform>`. Download it and
run, on Linux x86-64:

```bash
python scripts/record_golden.py --compare golden-mismatches-macos-arm64/
```

It recomputes those cases here and prints, per output, how many values differ, the largest
absolute difference and the largest ulp distance. For the replica, the job uploads the NIfTI
files that differ (`golden-mismatches-<platform>/afni-replica/`; the FSL replicas' in `golden-mismatches-gpl-<platform>/`).

## Recording

Checksums are recorded on **Linux x86-64 only** (both recorders refuse other platforms), from a
**committed** tree (the checksums name their commit) whose **parity passes**:

```bash
maturin develop --release
python scripts/record_golden.py           # runs the parity smoke tier first (in parallel: scripts/orchestration/parity_smoke.py; --serial-parity serially); refuses if it fails
git add tests/golden/golden.json && git commit -m "Record the golden checksums from <commit>"

pytest tests/parity/test_afni_tshift_replica.py   # the replica's parity first
LARMORX_GOLDEN_RECORD=1 cargo test --locked -p larmorx-cli --test afni_replica_golden
```

`record_golden.py --skip-parity` and `--allow-dirty` (`LARMORX_GOLDEN_ALLOW_DIRTY=1` for the
replica) exist for development; the file then says so (`"parity": "skipped"`, a `+dirty`
commit). `record_golden.py --check` compares without writing.

Re-record when a change alters an output on purpose (a fix, a new default): the diff of
`golden.json`, one line per output, shows exactly which outputs changed. Never re-record to make
another platform pass.
A new version re-records nothing: the harnesses write the running version as `<version>` (the
HDF5 writer's `/OSVersion`, tedana's `dataset_description.json`; since 2026-11-10).

## Resolved: numpy's 4×4 matrices (2026-10-11)

**What it was.** `lx.transforms` computed its 4×4 matrices in Python with numpy, with the same
expressions as nitransforms and fMRIPrep: `np.linalg.inv(vox2ras)`, `ras2vox @ M @ vox2ras`
for head motion, the ITK-to-RAS conversion `LPS · C⁺ · M · C⁻ · LPS` of every loaded
transform, `~Affine`, `DenseField.inverse`, and the products and SVD in
`ensure_positive_cosines`. numpy hands them to BLAS and LAPACK (OpenBLAS on Linux and Windows,
with kernels picked by CPU at run time; Accelerate on macOS), so their last bits depend on the
CPU and the platform. CI run 38095330520 confirmed it: four `lx.transforms` cases differed
between platforms (`py.transforms.resample_series`, `out.float64`, 36-112 ulp, up to 8e-13;
`py.transforms.resample_series.sdc`, `out`, 21 ulp; `py.transforms.files` and
`py.transforms.ensure_positive_cosines`, 1 ulp), and Windows x64 differed in that run but not
the previous one, as the runner's CPU changed numpy's kernel. Every other case was identical on
all six platforms, and so were the float32 outputs fMRIPrep writes.

**Result after the fix:** CI run 38100125479 (2026-10-11) passed every golden case on all six
platforms, in both packages.

**The fix (option 1 of the four weighed here before: Rust arithmetic in a fixed order).** The
products and inverses now run in Rust, `larmorx_transform::openblas`, in the operation order of
OpenBLAS 0.3.30's Haswell kernels, which numpy uses on x86-64 CPUs with AVX2 and FMA:
`dgemm` as fused multiply-add chains, `dgesv` as OpenBLAS's `getf2_k` and `getrs` with their
separately rounded dot products and reciprocal pivots, `dgemv` for a single point, and
`idamax`'s handling of NaN. `io_orientation`'s SVD is vnl's LINPACK SVD. The Python layer
evaluates nitransforms' expressions with these functions (`larmorx.transforms._linalg`). So:

- every platform and CPU computes the same bits (`f64::mul_add` is a correctly rounded fused
  multiply-add everywhere);
- on an x86-64 machine with FMA, larmorx stays bit-identical to fMRIPrep: 18,143,058 of
  18,143,058 compared results against numpy
  ([numpy-linalg.md](numpy-linalg.md)), and the resample-series parity is still 136 of 136
  bit-identical ([resample-series.md](resample-series.md));
- the recorded checksums did not change: they were recorded on this machine, where numpy
  already computed the Haswell bits. Three outputs were added so that CI also checks numpy's
  single-point order: `affine.one_point` and `field.one_point` in `py.transforms.map`, and
  `one_voxel` (a one-voxel target) in `py.transforms.resample_series`.

fMRIPrep's own results keep the dependence on numpy's kernel: SkylakeX (AVX-512), the kernels
without FMA, Accelerate and ARM differ from the Haswell bits
([numpy-blas.md](../findings/numpy-blas.md) has the measurements). The golden cases keep the
inputs that made the risk visible (rotation centres that are not dyadic, a float64 copy of the
resampled series), so a regression would show in CI.
